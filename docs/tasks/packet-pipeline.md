## Why this exists
FissionMC = vanilla 26.3 jar + Mixin + a port of Paper, GPL-3. Goal: several backend servers share one world through a master (decisions D1–D6 in `~/claude/memories/global/fissionmc/roadmap_detail.md` and `project_fissionmc.md`; read both plus `model1_worklog_node_network.md` and `worklog_replication.md` in the same folder).

**Decision D1: clients connect ONLY to the master.** To the client the master *is* the server; backends are invisible (no transfer packet, no reconnect when crossing a border). Today the master (`master/`) has **no client handling at all**: it only talks to backends over the node link (`net/`, Ed25519 mutual auth, heartbeat, reconnect; replication of block changes already works between two backends — see `docs/replication-demo.md`). This task builds the missing half: the packet pipeline, i.e. how a real Minecraft client reaches the network, and a PacketEvents-style API that governs packets in the core instead of through a plugin.

User's original goal 3: "govern packets like PacketEvents does but through the software itself instead of through a plugin API", and plugins that depend on PacketEvents should keep working without installing it (a built-in virtual plugin named `packetevents`).

## What already exists to build on
- `packetevents/api` and `packetevents/netty-common`: PacketEvents (GPL-3.0, vendored, pinned by `upstream/upstreams.toml`, re-vendored by `scripts/upstream.py`; local changes must go in `upstream/patches/packetevents/*.patch`). Its `api` module is platform-independent: packet wrappers, `PacketType`, encode/decode, event system, user/player data. Its `spigot` module (injector) was deliberately NOT vendored: our own platform module replaces it.
- `net/`: `NettyTransport`, `NodeLink`, framing, handshake, `NodeClient`. `protocol/`: node messages — **message ids are wire format, never reuse** (ids 0–20 core/world, 32–37 replication; pick a new range, document it in `protocol/.../`).
- `master/`: `MasterMain`, `MasterServer`, `NodeRegistry`, `ReplicationHub`. `backend/.../node/NodeBootstrap.kt` (modes standalone / backend / combined) with `addMessageHandler` as the hook for new subsystems.
- Language rule: FissionMC's own logic is **Kotlin**; Mixin shims stay thin **Java** in `backend/src/main/java/.../mixin/` (use NEW files named `*PacketMixin`, never edit the Paper-port mixins). Mixin constraints: non-private fields/static methods are rejected — make them private and declare widening in `surface/members/*.txt`.
- Build: `distrobox enter claude -- bash -lc "cd ~/Downloads/code/FissionMC && JAVA_HOME=/usr/lib/jvm/java-25-openjdk bash gradlew <tasks> --no-daemon -q"`. Tests: `:net:test :master:test`. Boot a master: `:master:run`; backend: `:backend:run -PrunDir=run-a -Pport=25566` (`run-*/` gitignored). `run/eula.txt` exists (user-set); never edit it.
- Do not launch the Minecraft client yourself; the user tests with their own client (a hand-written encoder and a hand-written decoder will always agree with each other — see memory note on the dead beacon project — so wire correctness needs the real client or PacketEvents' own codecs as the single source of truth).

## Milestones (in order; commit after each; report after each)
**P0 — design note (short, before code).** Write `docs/design/packet-pipeline.md`: (a) how PacketEvents `api` is used standalone on the master (no Bukkit, no NMS) and on backends (encode/decode vs NMS `StreamCodec`), (b) the master↔backend *player relay* design (see P2), (c) threading (Netty event loop per client; lobby logic on its own executor; never block the loop), (d) where the PacketEvents-style API lives so plugins and core share it, (e) risks. Flag any decision you need from the user as a question at the end instead of guessing.

**P1 — master accepts real clients (status + login + limbo).**
- Netty server listener on the master (port configurable, default 25565), handshake/status (MOTD + protocol version 26.3, player count from the registry), login with **online-mode authentication** (Mojang session server `hasJoined`, RSA key exchange, AES encryption, compression threshold) and an offline-mode switch for dev, configuration phase, then play: a **minimal limbo** — join game, spawn position, an empty/void world with a small platform if needed, keepalive, chat message "waiting for a backend", clean disconnect on quit. Use PacketEvents wrappers for every packet. Config-driven (`run-master/fission.properties`).
- Verify with unit tests where logic is pure, then **ask the user to connect with a real client** and give exact steps. Do not claim it works until the user confirms.

**P2 — relay a player to a backend.** Design + implement the minimum: after login the master picks a backend (round robin / first alive) and relays the player's packets over the existing `NodeLink` as framed messages (new ids, e.g. `PlayerAttach(playerId, uuid, name, profile properties, protocol)`, `PlayerPacketToBackend(playerId, bytes)`, `PlayerPacketToClient(playerId, bytes)`, `PlayerDetach`). On the backend, create a virtual client connection (Netty `EmbeddedChannel`/local channel wired into vanilla's `ServerConnectionListener`/`Connection` via a thin Java Mixin) that skips login (like Velocity "modern forwarding": profile and UUID come from the master) and feeds the relayed bytes into the normal packet handler, so the player joins the backend's world like a real client. Backpressure and disconnect handling both ways. Replace the limbo with the backend once it is up (limbo stays as fallback when no backend is alive).

**P3 — in-core packet listener API.** Our own platform module for the vendored PacketEvents `api` (replacing its spigot injector): events for packets in each direction on master and backend (receive/send, cancel, modify, priorities, per-user state), fed from the pipeline of P1/P2 on the master and from the virtual connection on the backend. Register a built-in virtual plugin named `packetevents` so `depend: [packetevents]` plugins resolve and `PacketEvents.getAPI()` works. Keep upstream-merge friendliness: do not edit vendored files except via `upstream/patches/`.

**P4 (only if still in budget) — merge/entity-id plan.** Write, don't build: how packet streams from several backends are merged into one client view (global entity id space, chunk ownership, keepalive/teleport-confirm bookkeeping) — extends the D6 note.
